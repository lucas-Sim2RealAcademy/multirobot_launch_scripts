## (b) What moved when the sim2real gap closed

**Stronger:**
- **#8 fis-bbox** and **#7 alignment.** Both reproduce identically post-gap and are pure launch/param logic with no coupling to sensor rates. `fis_fast4_{delta,ghost,buckshee,thunderstrike}.log:4` all print the same `AABB [-10.0,-10.0,0.0]->[10.0,10.0,3.0]`; steady state `grid 401x401x61` = exactly the 20×20×3 m slab at nvblox's 0.05 m voxel. `coord_fast4_*.log:9-12` show vehicles 1 and 3 `prior loaded`, vehicles 2 and 4 `prior MISSING (unaligned)`. With VSLAM divergence removed, these two config defects are now **the visible ceiling on exploration performance** — that is most of the story behind 26 FAIL → 13 FAIL.
- **#5 claim-frame.** The 3.5 m offset is now demonstrable with a *healthy* VIO: fast4 has three different reach frames in one fleet (v1 reference, v3 with a 3.5 m prior, v2/v4 unaligned) and nothing to blame it on.

**Weaker (evidence retracted, verdict intact):**
- **#2 vio-bridge-lies.** The headline numbers were rig artifacts and must not be quoted: `viobridge_hw4.log:3` `pos_ned=(2552.246, -1515.167, -212.689)` and `viobridge_ev1.log` `|v|=1276.8 m/s` were 2.6 Hz-stereo divergence. Note these were all `CUVSLAM_SUCCESS` — "Visual tracking is lost" appears once in the entire pre-gap log set — so the failure mode was **silent SUCCESS-drift**, where a `vo_state` gate would not have helped and only the covariance channel would. The defect now rests on source + params + their own `log_57`. It does *not* go fully weak, because `cuvslam_stutter_per_min` is still **805–830/min with 280–343 ms max frame deltas on all four drones** post-gap (`scorecard_fast4.txt`, FAIL vs a `<=2` reference) — the jitter precondition is reduced, not closed.
- **#6 odom-guard.** The specific 10 m / 2 s jump we watched in coord4 was rig-caused (cuVSLAM starved). The defect that remains is the *total absence of a detector*, which is a source fact, with the field trigger independently evidenced in their ulg.

**Neither — and one scorecard row is a false pass:**
- **#1 visited-blackout.** The apparent "ghost NO PATH 120 → 0" improvement is a **null result**. All four `planner_fast4_*.log` are 140-141 lines of nothing but `INIT: odom=False front=False armed=False offboard=False debug=True` (139-140 occurrences each; `PLAN OK` = 0, `NO PATH` = 0). The planner never left `State.INIT` because the gate at `:899-900` never passed — it received neither odometry nor frontiers for 264 s despite cuVSLAM running at ~29.5 Hz in the same run. `Path complete` is the sole writer of `visited_positions` and fired zero times, so **the code path was never executed**. Treat `scorecard_fast4.txt` `no_path_count[*] = 0 PASS` as **void**; the adjacent `planner_p95/max_ms = 1 ms` is the tell. `git log -S"visited_radius"` and `-S"spec: hard zero"` confirm no upstream fix exists — the 60 s / 1.5 m hard zero is live on `sim` and on `main`'s lineage today.
- **#3 radio-remaster / #4 lora-eof.** Structurally unmovable by the gap: `scorecard_fast4.txt` lines 10/20/30/40 report `lora_attached = 0, FAIL(radio dead)` on all four drones, and no `"opened LoRa serial:"` line exists in any `coord_fast4_*.log` — `find_lora_port()` returned None (no CP2102 in sim; `coordination_stage.launch.py:52-53` passes no `serial_port` param), so the bridge sat in the benign no-port 2 s backoff and the ESP32 firmware never executed at all. Absence of log evidence is not exculpatory here; both stand entirely on source + reproduced kernel/tty semantics.
