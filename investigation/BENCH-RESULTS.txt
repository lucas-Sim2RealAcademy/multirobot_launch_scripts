DEFECT FOUND (blocks anyone testing depth-rate reduction)
  HERC_DEPTH_HZ=10 (integer) kills all four sensor nodes at startup:
    terminate called after throwing rclcpp::exceptions::InvalidParameterTypeException
    parameter 'depth_hz' has invalid type: parameter {depth_hz} is of type {double},
    setting it to {integer} is not allowed
  airsim_realsense_node.cpp declares stereo_hz/depth_hz/imu_hz as double, and
  run_fleet_radio.sh passes HERC_* through verbatim.  Must be 10.0 / 15.0 / 5.0.
  Symptom downstream: run_exp.sh reports PLAN_OK=0 on every drone and archives _INVALID.
  Hit by the sibling agent's r2_depth10 and r2b_depth10 runs.

DEFECT FOUND (silent, cosmetic but misleading)
  fidelity_scorecard.sh greps rsnode/planner/fis logs without -a.  Those logs contain NUL
  bytes, so grep prints "binary file matches" and the metric is scored 0.00 -> FAIL.
  Seen throughout e1_frames/scorecard_fast4.txt.

DEFECT FOUND (silently returns a 256x144 image)
  settings-fleet-4drone.json declares CaptureSettings for front_center only for ImageType 1
  (DepthPlanar).  Requesting DepthPerspective from that camera returns AirSim's 256x144
  default, not 640x480.  Anyone implementing VIO-STABILIZATION-PLAN R11 (DepthPerspective +
  cosine LUT) must add a CaptureSettings entry with ImageType 2 first.

MY "THE MODEL CLOSES" CROSS-CHECK: still don't trust it, but my RETRACTION overstated it.
  I first claimed 157.13/12 = 13.1 Hz "exactly" matched the observed 13.1-13.8.
  I then retracted that using depth=30, getting 18.7 renders/fleet-cycle -> 8.4 Hz, and
  said the model under-predicts by 60%.  That retraction ALSO used the setpoint.
  With delivered depth: 2*13.1 + 13.8 + 5.9 = 45.9 renders/drone/s = 3.50 per stereo cycle,

THE BLOCK 4 CEILINGS ARE NOT ABSOLUTE CEILINGS (weaker than I first said, but still true).
  Full-stack totals reach 172.8-193.2 renders/s against the isolated best-of-3 "ceiling"
  of 157.13, i.e. 1.10-1.23x above it.  (I earlier claimed 250.6 = 1.59x; that used the
  30 Hz setpoint and is withdrawn.)  1.10x is inside the noise floor; 1.23x is not.  The
  ladder ran against background load 9.5-10.5, so its absolute numbers are depressed.
  Block 4 stays valid for RELATIVE resolution/concurrency comparison (both arms equally
  contended) and must not be used as an absolute budget.

WITHDRAWN: my "34% conversion efficiency" figure.  It divided by 80 renders/s of freed
  capacity computed from the SETPOINT.  Recomputed on delivered depth the freed capacity
  is (14.6-9.4)*4 = 20.8 r/s against 27.2 r/s absorbed, i.e. 131%.
  DO NOT PUBLISH 131% EITHER.  It is a ratio of two small differences, each built from
  rates carrying ~11% run-to-run error; its error bars span roughly 50-250%, and the
  underlying total moved only 172.8 -> 179.2 (+3.7%), well inside noise.  The whole
  "conversion against a render budget" frame should be dropped for both levers.

THE ACTUAL DISCRIMINATOR IS THE RESOLUTION A/B, NOT THE DEPTH ARITHMETIC.
  The depth numbers cannot separate "fixed render budget reallocated at ~100%" from
  "throughput elastic in round-trips" -- both predict what was seen, within noise.
  The resolution A/B separates them cleanly: making every render ~1.9x cheaper enlarges a
  render budget but does nothing to round-trips.  Delivered stereo went 17.7 -> 16.8 at
  matched load (r5 8.9 vs r6 8.8) and total throughput 179.2 -> 168.4.  No gain, slightly
  negative.  Therefore render time was never the scarce resource.
  Why depth 30->10 helped anyway: it deletes ~5 blocking RPC round-trips/s/drone
  (14.6 -> 9.4 Hz) plus the matching nvblox integration CPU.  It is a round-trip lever
  that was mislabelled as a render lever, which is exactly why resolution -- a pure
  render lever -- returned nothing.

BINDING CONSTRAINT: RPC round-trip + CPU/GPU contention with the consumer stack.
  airsim_realsense_node.cpp:11 documents ~30 ms per blocking simGetImages call = ~33 Hz
  per connection before contention.  At 17.7 Hz the stereo connection is at 56.5 ms,
  i.e. ~26 ms of contention on top of the floor.

WHY THE RESOLUTION NULL IS TRUSTWORTHY WHILE THE DEPTH RATIO IS NOT
  Both rest on the same sloppy per-run numbers, so the difference is effect size vs noise:
    ladder predicted 17.7 x 1.90 = 33.6 Hz for 424x240
    best SINGLE 424 observation   18.6 Hz  -> 44.7% below prediction = 4.3x the noise floor
  A null that misses its prediction by 4x the noise survives noisy inputs.  A ratio of two
  small differences (the 131%) does not: propagating +/-10.5% through all four underlying
  rates puts it anywhere from 1% to 501%.  One clean experiment beats three noisy ones
  chained into a ratio.  Both agents independently built a headline on such a ratio today.

OUTCOME (sibling agent, closing the loop -- the reason any of this mattered)
  The 25 Hz "gate" was a false premise: a nominal 30 Hz frame period that hardened into a
  numeric target.  The real criteria are image_jitter_threshold_ms:=200.0
  (run_fleet_radio.sh:176) and a field reference of <=2 cuVSLAM stutters/min.  At
  17.7-18.7 Hz all four drones sit at 0-4 stutters/min, so VIO was never starved at the
  stock defaults and the rate work was never on the critical path for tracking quality.
  THE WIN WAS EXPLORATION, NOT VIO.  HERC_CAPTURE=0 + HERC_DEPTH_HZ=10.0 took the stock
  fleet from ~460 to 547 mean unique m2 (+19%), best run 607/630 = 96% arena coverage at
  excess 2.6 -- the first PASS in this archive.
  LADDER A/B RE-RUN at the corrected operating point, n=3 per arm interleaved: REGRESSED.
  unique 547 -> 409 (-25%), excess 9.9 -> 30.8 (+211%), consistent across all three pairs,
  constraint verifiably enforced (min goal 1.0-1.1 m vs 0.2-0.4 m) and the planner never
  starved (NO PATH 1-3, dead-zone fallback fired zero times).  So the deadband is real but
  suppressing it costs more than it saves -- the nearest-frontier micro-hop was doing useful
  work.  Reverted, nothing stacked.  Config restored to 640x480 on all four vehicles.

RETRACTED: the host-side stereo-matcher idea (drop the depth render, "x1.5").
  It was sized on the render budget, and the render budget is not binding.  It would free
  a resource that is not scarce while ADDING GPU contention to the resource that is.
  Expected effect on delivered stereo Hz is neutral-to-negative.  Do not build it on my
  earlier reasoning.

UNTESTED HYPOTHESIS, offered as the one thing the mechanism actually points at:
  connection parallelism, not cheaper renders.  Block 1 showed strongly superlinear
  scaling in connection count (scene: 7.57 renders/s at n=1 -> 80.60 at n=4), i.e. the
  renderer overlaps work across connections that it cannot overlap within one blocking
  call.  The stereo pair is currently TWO renders inside ONE blocking simGetImages.
  Splitting left/right onto two connections (8 -> 12 connections fleet-wide) would let
  them overlap.  Nobody has measured this.  Given that two "obvious" render levers have
  already behaved contrary to prediction here, measure it before believing it.
  WHY IT IS THE RIGHT NEXT EXPERIMENT, beyond being the only live thread: it is cheap to
  test AND cheap to be wrong about.  It changes how many simGetImages calls the stereo loop
  issues, not what gets rendered -- so it costs no fidelity, needs no settings change, and
  reverts by editing one loop.  Both levers burned today required either a fidelity trade
  (resolution) or a planner change (ladder) merely to EVALUATE.  Instrument the ROUND-TRIP
  count, not the render count: that is the resource the evidence says is scarce.

MEASURING ANYTHING ON THIS HOST -- READ BEFORE TRUSTING A SINGLE NUMBER ABOVE
  Nearly every figure in this file was distorted at some point by another agent
  benchmarking on the same box, and both agents involved threw away runs to discover it.
  Observed swing from contention alone, same config: 17.7 Hz at load1 8.9, 10.7 at 11.8,
  6.2 at 16.4 -- a 2.9x range, larger than every render lever in this file COMBINED.
  The +/-11% noise floor quoted above assumes the host stays roughly as loaded as it was
  during these runs.  Without either single-tenancy or an enforced lock discipline it
  quietly becomes +/-100%, and every conclusion here becomes unfalsifiable.
  Minimum practice: record load1 on EVERY row (all tables above do), compare only within
  a matched-load block, interleave A/B arms rather than running them in sequence, and take
  replicates of the SAME config to establish the noise floor before believing any delta.
  A .HOST_LOCK convention was used during this work but nothing enforced it -- three agents
  ran concurrently anyway, two of them under process names deliberately chosen so that
  pkill -f "UnrealEditor.*Blocks" would not match them.
