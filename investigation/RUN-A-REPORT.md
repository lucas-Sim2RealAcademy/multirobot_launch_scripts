# Run A Report — coord4: field-faithful 4-drone coordinated exploration (2026-08-13, ~226 s, Blocks arena)

**Rig:** per-drone real cuVSLAM + odom_correction + nvblox + FIS + simple_exploration_planner + real coordination stage (coordination_node / alignment_manager / keyframe_exchange / peer_map_integrator / lora_bridge with no radio) + 4x zenoh-bridge-ros2dds on loopback, ROS domains 1–4 (ghost=1, delta=2, buckshee=3, thunderstrike=4), spawns 3 m apart, flight_height 1 m, planner bbox ±10 m in each drone's own odom frame.

**One-paragraph verdict:** Ghost's NO PATH x120 is a **new code-fault in the planner's visited-set filter** (a hard 60 s planner blackout), not any cataloged bug, with a rig-known cuVSLAM jump as a compounding co-event. The headline triage is misleading: the three "clean" drones suffered *worse* VIO divergence than ghost and physically flew 23–93 m out of the arena at up to 6.6 m altitude with no abort — PLAN_OK/EXEC/NO_PATH counts are not valid health metrics for this run. The coordination layer's no-radio degradation behaved exactly as designed, but the zenoh mesh was **dead the entire run** (all 4 bridges panicked at startup on a rig config fault), so Run A validates nothing about cross-drone exchange and leaves F8 untested.

## 1. What happened to ghost

**Root cause (decisive): visited-set hard-zero starvation — CODE-FAULT, new, not in the catalog.** Two distinct phases, only the first is the NO PATH stall:

**Phase 1 (t+24 → t+84): the NO PATH x120 blackout.** At `1786613543.601` ghost logged `Path complete at (1.0,-0.3)`, adding a visited entry (`simple_exploration_planner.py:398-399`: `visited_cooldown_s = 60.0`, `visited_radius = 1.5` m; hard score=0 inside the radius). One planning tick later (`1786613544.051`) the first `NO PATH: no clusters | took 0ms` fired, repeating 120x at 2 Hz through `1786613603.551` — while FIS concurrently published `FIS: 22 clusters, 1147 cells` at 1 Hz the entire window. The only scorable viewpoints ((1.2,0.0), (1.3,-0.3), (1.1,0.1)) all sat 0.3–0.4 m from the visited point and were hard-zeroed.

The smoking gun is the recovery: `PLAN OK: 2 wps, goal=(1.2,0.0), dist=10.5m ... wp0=(7.7,-8.1), took 16ms` at `1786613604.067` — **60.47 s after Path complete, the first tick after the 60.0 s cooldown expired**, to a goal 0.36 m from the expired visited point. Critically, ghost's believed pose was identical before and after recovery (frozen at (7.7–7.8, −8.1..−8.4) throughout), so the bbox-filter reading of this stall (the F1c interpretation reached independently by two analysis areas) is **wrong**: nothing about the bbox state changed at t+84; the only time-varying quantity was the visited cooldown. Catalog disposition:

- **NOT F2** despite the identical `NO PATH: no clusters | took Xms` string — peers were provably inert all run (`peers { 2: ok=0 gated=0 buf=0 src=- | 3: ... | 4: ... }` every 10 s; peer discounts are guarded by `if COORD_OK and self.peer_claims/positions`).
- **NOT F1g** — zero `Waypoint outside geofence, skipping` lines in ghost's log (delta has them; ghost does not).
- **F1c-family only** — same shape (planner starves while FIS is healthy) but the starving filter is the visited-set, not the bbox. Treat as a new catalog entry.

Two aggravating sub-defects: the stuck-relaxation (`Stuck (N failures) — using relaxed threshold 1.0m`, N=3..120) only relaxes the ESDF collision threshold and never the visited filter — 117 consecutive no-op relaxations; and the `NO PATH: no clusters` string (source line ~1172) is emitted when clusters exist but are all score-zeroed, which actively misdirects triage toward F2.

**Phase 2 (t+84 → SIGTERM): EXEC livelock — RIG-triggered, code-exposed.** Concurrent with phase 1's onset, cuVSLAM silently jumped ghost's pose (1.5,−0.6)→(8.0,−7.5) in <2 s (no reset/relocalization logged, only continuous `Delta between current and previous frame [350-495 ms] is above threshold [34.000000 ms]`; 503 stereo pairs in ~190 s = ~2.6 Hz effective under 4-drone load) and then latched at (7.8,−8.4). Ground truth (coord4_ghost meta JSONs): the drone was physically hovering ≤2.0 m from spawn all run (final ned (1.02,1.15,−1.25)). Result: PLAN OK at t+84, EXEC dist pinned at 10.45–10.77 m for 114 s (progress measured against the frozen estimate), `Replan timeout (30.5s)` x3 (`1786613635.07 / 666.07 / 697.07`), each re-planning the identical goal (1.2,0.0) until signal 15. The trigger is the rig-known cuVSLAM drift/stutter effect (EXPECTED-DEGRADATION), but it exposes real code gaps: no odom-discontinuity guard (a >10 m/2 s jump produced no reaction) and no no-progress escalation.

**Why ghost, not the others:** ghost is the only drone that *completed* a path before the fleet-wide VIO collapse — the completion is what armed the visited-set blackout. Delta never logged Path complete, so its lone cluster was never zeroed and it "scored clean" while its estimate careened 2 km off. Ghost's 120 NO PATHs mark the *least* physically degraded drone of the four.

## 2. Coordination layer verdict

**As-flown LoRa degradation: CONFIRMED, behaved as designed.** Exactly one lora line per drone (`lora_bridge up (topics under "lora/", baud 115200)`) and then silence for 200 s. Source-verified: `find_lora_port()` returning None makes `_open()` return False with no log line and the reader thread back-off silently — absence of `opened LoRa serial` on all 4 drones is the positive no-radio signature. Empty swarm/peers end state achieved. coordination_node ran its 190 ms (~5.3 Hz) cycle on all 4; keyframe_exchange and peer_map_integrator ran to end-of-run with zero tracebacks; claim set counts exactly equal PLAN_OK counts (the layer invented nothing).

**Zenoh mesh: NOT REAL this run.** All four zenoh-bridge-ros2dds processes panicked at `1786613518.142` — ~2 s before any ROS node existed — with `lo: the same interface may not be selected twice` → `panicked at zenoh-plugin-ros2dds/src/lib.rs:464:14: Failed to create RosDiscoveryInfoMgr: "Error creating DDS Reader on ros_discovery_info: Precondition Not Met"`. Cause: `ros_localhost_only: true` injects `lo` into the CycloneDDS interface list while the rig's CYCLONEDDS_URI also pins `lo`. No restart, no session, no route, zero bridged bytes for 226 s. This is a **rig launch-config fault, not the intended degradation**: Run A's design was "LoRa dead, zenoh up," and that intent was not met. The empty-peers state is therefore over-determined (radio dead AND bridge dead), and the keyframe/alignment/octomap exchange path was never exercised — "ran without crashing" is all Run A certifies about it.

**F8: NOT TESTABLE — carry forward.** The generated 22-pattern allowlist loaded and parsed correctly (2 global + 5 patterns x 4 drones visible in each bridge's Config dump), but the routing layer died before topic discovery. The observed outcome (nothing semantic bridged) matches F8's prediction while being fully explained by the crash. Neither confirmed nor refuted; Run B must resolve it.

**Live-run landmines found in the layer (inert this run):** (a) alignment prior asymmetry — vehicles 2 and 4 launched `prior MISSING (unaligned)` (swarm_alignment.yaml only carries priors for 1 and 3), so d2/d4 report `aligned_self=False` and would gate/discard peer maps in any live-radio run; (b) claim reach-check frame mismatch — ghost's claim (1.2,0.0) released `reached` at `1786613605.084`, 1.02 s after set, while the planner-frame vehicle was 10.5 m away (reach test runs in the PX4 local frame against a planner/odom-frame point; the frames disagreed by ~10 m after the VIO jump); (c) `radio OK` in the coordination_node banner means "radiohive msg package imported," not RF health — it printed on all 4 radio-dead drones.

- **Coverage overlap: 0 cells** for every pair (1 m cells, spawn-offset-corrected world frame) — but not because coordination worked: ghost covered 4 cells, delta ~21 (transit), thunderstrike ~27 (transit), and three drones left the arena on runaway odometry. All other pairs ≥3.0 m. - **Structural duplicate sweeps:** all four planners chose the identical first goal (1.3,−0.3)±0.1 *relative to their own spawn* (four PLAN OK quotes, t=21.5–34.5). With 3 m spawn spacing and no peer input, solo fallback produces parallel offset copies of the same pattern by construction.

Effective stereo 2.4–2.9 Hz on every drone from startup (503/529/589/538 pairs) vs cuVSLAM's 34 ms expectation — ~10x starved. VIO divergence was motion-triggered on all four (blowup 2–5 s after each drone's first waypoint motion: ghost t+24, delta t+31.4, thunderstrike t+36.6, buckshee t+39.5).

The only valid health metric this rig produced is physical-vs-believed divergence (meta ned vs planner pos) — captured for ghost only this run.

## 4. New bugs worth reporting (ranked)

**Loud catalog flag first — F1a (phantom-ground walls=0):** the signature string appears in essentially every ESDF line fleet-wide (ghost 94/94, delta 12/12, buckshee 13/13, thunderstrike 11/12) — flagged loudly per instruction. **Verdict: NOT confirmed as a regression.** Thunderstrike logged `walls=20` once (counter provably live post-fix), and no drone's known-cell count exceeded ~150 (maps never grew — VIO pinned/diverged every drone), so zero walls inside a tiny known set is physically plausible. Requires a dedicated healthy single-drone run near a block to close (see §5).

1. **No runaway / odom-sanity abort — CODE-FAULT, WILL occur in field.** Planners maintained EXECUTE with believed dist 59–2118 m (bbox ±10) while drones physically flew 73–93 m out at 4.8–6.6 m altitude; buckshee `EXECUTE ... dist_to_wp=163.818` at `1786613661.240`; delta CSV tail dist 2118.6 m. No check aborts flight when believed position exits the planner bbox or dist-to-goal explodes. In the field, VIO degradation (dust, vibration, low light — the premise of odom_correction) turns this into a physical flyaway. Highest-severity finding of the run.
2. **Visited-set 60 s planner blackout — CODE-FAULT, will occur in field.** Ghost's NO PATH x120: window bounded exactly by `visited_cooldown_s` (starts 1 tick after Path complete, ends first tick after expiry, 60.47 s), all candidates inside the 1.5 m hard-zero radius, FIS healthy throughout. Fires any time remaining frontier viewpoints cluster within 1.5 m of a just-completed endpoint (confined pockets, exploration tail) — a 60 s minimum hover per occurrence, repeatable. Ship with two sub-fixes: the misleading `NO PATH: no clusters` string when clusters exist but are score-zeroed, and stuck-relaxation never relaxing the visited filter (117 no-op relaxations here).
3. **Claim reach-check frame mismatch — CODE-FAULT, will occur in field.** `claim set: (1.2, 0.0)` at `1786613604.067` → `claim released: reached` at `1786613605.084` while the planner-frame vehicle was 10.5 m away. PX4-local-frame position tested against a planner/odom-frame claim point with `claim_reach_radius_m=1.0`. Inert with empty peers; with live claims (Run B, field) it releases claims prematurely and lets peers steal frontiers the owner is still flying toward.
4. **splanner CSV filename collision — CODE-FAULT (logging), rig-blocking.** Second-resolution timestamp filenames with no drone/domain ID: 4 planners → 2 files, interleaved writers, torn rows (`1786613627.1786613627.858`; 67+19 corrupt rows), buckshee and ghost telemetry mostly lost. Field risk low (per-drone filesystems) but it invalidates every multi-drone rig analysis — fix before Run B.
5. **Alignment prior gap for vehicles 2/4 — RIG-ARTIFACT (config) with field consequence if the yaml ships.** `prior MISSING (unaligned)` on d2/d4, `aligned_self=False` all run. In any live-exchange run, half the fleet gates/discards peer maps.
6. **Zenoh bridge duplicate-`lo` startup panic — RIG-ARTIFACT, not a field mode** (field doesn't bridge over loopback), but it silently voided Run A's coordination objective and will void Run B's if not fixed. Add a launch-time health gate (see §5).
7. **`radio OK` health-label — CODE-FAULT (observability), will occur in field logs.** Prints when the radiohive msg package imports, regardless of RF state; combined with lora_bridge's silent-by-design retry loop, a field log of a radio-dead drone contains zero affirmative evidence of the failure. Rename to `msgs OK` and add a periodic `no LoRa port` warn.
